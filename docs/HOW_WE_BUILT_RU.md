## Часть 1. Как мы это делали

### Отправная точка

Кейс 2 «Smart Caspian Transit» требовал три вещи MVP:

- **Предиктивная модель.** Прогноз задержек мультимодальной перевозки по истории, погоде на Каспии и загрузке портов.
- **Смарт-контракт / цифровой коридор.** Автоматическое таможенное предоформление на распределённом реестре или защищённых API.
- **Единое окно логиста.** Цифровой двойник груза, углеродный след (ESG) и альтернативные маршруты при форс-мажоре.

Стек из ТЗ: predictive analytics, графовые БД, API-интеграции, блокчейн / смарт-контракты (опционально), цифровой двойник.

У нас уже был первый прототип: FastAPI-бэкенд с моделью задержек, React-интерфейс с картой и SQLite. Это коммиты `Initial project commit`, `Rework delay prediction` и `Frontend redesign`.

### Как была организована работа

- **ИИ-агенты.** Код писали с помощью ИИ-агентов (Claude Code). Один агент координировал работу и брал сложные части на себя. Отдельные агенты параллельно делали независимые функции: погоду и модель, реестр, граф, тексты интерфейса.
- **Изоляция.** Каждый агент работал в своей копии репозитория (git worktree) и в своей ветке. Потом всё сливалось в `demo/final`.
- **Проверка после каждого слияния.**
  - Полный набор тестов: сейчас 847.
  - Сборка фронтенда.
  - Сквозной сценарий `scripts/demo.py` против собранного Docker.
- **Ветки.** Всё лежит в `demo/final`, открыт pull request в `main`.

> **Если жюри спросит «вы это писали с ИИ?»** — отвечайте честно. Да, мы использовали ИИ-агентов как инструмент разработки. Решения по архитектуре, проверке и демонстрации — наши. Покажите, что понимаете каждую часть: для этого и нужна часть 2 ниже. Хуже всего — не суметь объяснить собственный код.

## Часть 2. Что выучить

Учите по уровням. Уровень A обязателен каждому, кто выходит на сцену. B — тем, кто отвечает на технические вопросы. C — для уверенности.

### Уровень A — обязательно всем (≈1 час)

**1. Питч за 30 секунд, своими словами.**

| Пункт ТЗ | Экран | Что показать |

- Коэффициенты CO₂е иллюстративные.

### Уровень B — для технических вопросов (≈3 часа)

Для каждой темы: что понять, где прочитать, на какой вопрос уметь ответить.

**Модель** — [`PROJECT_GUIDE_RU.md` §3a](PROJECT_GUIDE_RU.md), `backend/app/predictive.py`, `data.py`

- **Градиентный бустинг.** Много маленьких деревьев решений, каждое исправляет ошибки предыдущих. У нас `HistGradientBoostingRegressor` из scikit-learn.
- **Монотонные ограничения.** Модели запрещено снижать задержку при росте ветра, волны, очереди или опоздания. Это делает её объяснимой и защищает от абсурдных прогнозов.
- **Входы:** ветер, осадки, волна, очередь, накопленное опоздание, масса. **Выход:** дополнительная задержка в часах. Вероятность срыва считается по разбросу ошибок модели и запасу времени до отхода.
- **MAE и ROC AUC.** MAE — средняя ошибка в часах. ROC AUC — вероятность, что модель поставит случай со срывом выше случая без срыва: 0,5 — монетка, 1,0 — идеал.
- **Хронологическое разделение.** Учимся на ранних записях, проверяем на поздних. Перемешивать нельзя: иначе будущее подсмотрено.
- **Почему AUC не 1,0.** В историю специально заложены факторы, которых модель не видит: поломки кранов, выборочный досмотр, сдвиг отхода парома. Даже «всезнающая» модель дала бы около 0,94.
- ❓ *«Чем ваша модель лучше среднего?»* — В 3,3 раза меньше ошибка, проверено на будущем периоде, которого модель не видела.

**Погода** — `backend/app/weather.py`

- Open-Meteo: бесплатный API без ключа. Один пакетный запрос на все порты (ветер, осадки) и морской запрос для волны.
- Кэш на 30 минут. Таймаут 3 с.
- Если сервис недоступен — берём последние живые данные. Если их нет — резервные синтетические. Источник всегда подписан в интерфейсе.
- ❓ *«Что будет без интернета?»* — Сайт работает. Погода переключится на резервную, и это будет видно в подписи.

**Граф коридора** — [§3b′](PROJECT_GUIDE_RU.md), `backend/app/graphdb.py`

- Neo4j: хабы — узлы `(:Hub)`, рейсы — связи `[:SERVICE]`.
- Запрос Cypher ищет все цепочки рейсов от точки А до точки Б, исключает закрытые рейсы и повторы хабов.
- Расписание и стыковки по времени проверяются в Python. Граф отвечает на вопрос «какие цепочки вообще существуют».
- Если Neo4j недоступна — тот же расчёт делает networkx. Результаты проверены на совпадение тестом.
- ❓ *«Зачем графовая БД, если узлов 8?»* — Сеть коридора по природе граф. При сотнях хабов и тысячах рейсов поиск обходов — именно то, для чего Neo4j создана. Модель данных уже готова к росту.

**Смарт-контракт** — [§3e](PROJECT_GUIDE_RU.md), `backend/app/preclearance.py`

- **Жизненный цикл:** черновик (версии) → проверка (сверка документов) → отправка → решение.
- **R1** — документы согласованы: номера контейнеров и массы.
- **R2** — код ТН ВЭД не из списка ручного контроля.
- **R3** — стоимость за кг в правдоподобных пределах.
- **R4** — отправитель в списке доверенных (аналог AEO).
- **R5** — страна происхождения разрешена.
- **Решение.** Все правила пройдены — статус «Принята» автоматически. Иначе — к инспектору. Брокер не может принять собственную декларацию.
- **Хэш правил.** Подменить правила незаметно нельзя. **Идемпотентность:** повторная отправка не создаёт второе решение.
- ❓ *«Это настоящий смарт-контракт?»* — Это исполняемые версионируемые правила с хэшем и журналом, заверенным узлами. ТЗ допускает «распределённый реестр или защищённые API», и мы закрываем обе формулировки. Блокчейн с токенами здесь избыточен.

**Реестр** — [§3f](PROJECT_GUIDE_RU.md), `backend/app/ledger.py`, `witness_node.py`

- **Хэш-цепочка.** Каждая запись содержит хэш предыдущей. Правка старой записи ломает все следующие.
- **Узлы-свидетели.** Три отдельных сервиса, у каждого своя база и свой ключ. Они подписывают голову цепочки (HMAC). Кворум — 2 из 3.
- **Защита запросов к узлам:** подпись, метка времени ±120 с, одноразовый nonce. Подделанный или повторённый запрос отклоняется.
- **Состояния узла:** подписал / недоступен / расхождение / отстаёт.
- ❓ *«Почему не Ethereum / Hyperledger?»* — Для разрешённого круга участников (таможня, порт, перевозчик) достаточно кворума подписей. Это дешевле, быстрее и понятнее регулятору. Следующий шаг — асимметричные подписи и узлы у реальных организаций.

**Прогноз хабов** — [§3d](PROJECT_GUIDE_RU.md), `backend/app/hubs.py`

- Для каждого хаба по часам на 72 ч складываем тоннаж прибывающих грузов и фоновую загрузку, делим на пропускную способность (т/ч).
- Больше 100 % — узкое место. В интерфейсе показан список перевозок, которые попадают в это окно.

**ESG** — [§3g](PROJECT_GUIDE_RU.md), `backend/app/esg.py`

- CO₂е = масса (т) × расстояние (км) × коэффициент.
- Коэффициенты (кг CO₂е на т·км): ж/д 0,022, море 0,016, авто 0,105.
- Иллюстративные, не сертифицированы (не ISO/GLEC). Методика прозрачна и заменяема.

### Уровень C — для уверенности (по желанию)

- **Безопасность** ([§3i](PROJECT_GUIDE_RU.md)):
  - роли брокера и инспектора, токены;

## Часть 3. Шпаргалка к показу

Команды запускать **из папки проекта**, где лежит `docker-compose.yml`.

```bash
docker compose down -v && docker compose up -d --build   # чистый старт, ~1 мин
```

Открыть http://127.0.0.1:5173. Проверить, что погода подписана «Open-Meteo».

**Остановка узла реестра на сцене:**

```bash
docker compose stop witness-2      # «Порт · недоступен», запись всё равно заверена (2 из 3)
docker compose stop witness-3      # кворум не достигнут — система честно это показывает
docker compose start witness-2 witness-3
```

**Если что-то пошло не так:**

- *Декларация уже «Принята» с прошлого прогона.* Перезапустите с чистой базой: `docker compose down -v && docker compose up -d`.
- *Нет интернета.* Погода станет резервной, всё остальное работает. Для полностью повторяемых цифр: `WEATHER_PROVIDER=synthetic docker compose up -d`.
- *Neo4j не поднялась.* Маршруты посчитает networkx: в подписи источника будет «networkx», функциональность та же.

## Часть 4. План подготовки на день

1. **Утро, 1 ч.** Уровень A. Каждый проговаривает питч и цифры вслух.
2. **1 ч.** Двое прогоняют живой показ 3 раза подряд с секундомером, третий задаёт вопросы из [§6 гида](PROJECT_GUIDE_RU.md).
3. **2–3 ч.** Уровень B. Распределите темы: модель и погода, граф и маршруты, смарт-контракт и реестр, ESG и хабы.
4. **Вечер.** Полная репетиция: презентация (≈4 мин) + показ (≈3 мин) + 5 минут вопросов. Перед выходом — чистый старт Docker.
