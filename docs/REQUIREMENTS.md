# Требования и трассировка — Smart Caspian Transit, case 2

Первичный источник: `Keisy_khakatona_KTsF2026.docx`, кейс 2 «Предиктивный цифровой двойник мультимодального хаба». Рабочая интерпретация — по разборам `case2_smart_caspian_transit_plan.md` и `Smart_Caspian_Transit_razbor (1).md`.

Документ фиксирует **целевое соответствие** трём обязательным модулям ТЗ и способ проверки. Он не является отчётом о пройденных тестах: фактический статус на текущем коммите показывает `./scripts/check.sh`. Всё, что не входит в обязательные M1–M3 (AIS-live, Neo4j, LLM-агент, 3D, блокчейн-сеть), считается усилением и не выдаётся за требование.

## 1. Три обязательных модуля Word case 2

| Код | Модуль ТЗ | Обязательный результат |
|---|---|---|
| M1 | Предиктивная модель | Прогноз задержки/готовности мультимодальной стыковки по истории, погоде и загрузке портов; риск пропуска отправления и причины — до появления узкого места |
| M2 | «Смарт-контракт / цифровой коридор» | Прототип pre-clearance: подготовка и проверка документов, роли, версии, локальная тестовая подача, аудит; распределённый реестр **или** защищённые API |
| M3 | «Единое окно логиста» | Цифровой двойник груза, timeline, альтернативные маршруты при сбое, пересчёт ETA, стоимости и углеродного следа |

Сквозное требование: груз → событие (шторм/очередь/таможня) → прогноз → алерт → допустимая альтернатива → пересчёт ETA и CO₂. Без этого сценария отдельные модули не считаются решением.

## 2. Матрица трассировки

Колонка «Реализация» — целевые артефакты по `docs/PLAN.md`; доменные модули обмениваются JSON-совместимыми словарями, Pydantic валидирует на границе REST.

| ID | Требование | Реализация | Контракт / API | Приёмка |
|---|---|---|---|---|
| **M1-01** | Учитывать историю, погоду, очередь терминала и загрузку | `data.py`: ≥600 независимых строк за 90 дней, погода, очередь, масса, `hours_to_cutoff`; `predictive.py`: chronological split 80/20 | Поля истории из `CONTRACTS.md`; `GET /api/shipments/{id}`, `GET /api/model/metrics` | `tests/test_data.py`, `tests/test_predictive.py`; seed 42 даёт стабильные данные |
| **M1-02** | Прогнозировать задержку и время готовности, а не фиксировать факт | `predictive.py`: монотонный HistGradientBoosting + baseline; формула `ready_at = max(...)` без двойного учёта `observed_delay` | `Prediction.delay_hours`, `ready_at`; `ShipmentDetail.prediction` | Низкий ветер у SCT-001 даёт малую задержку; шторм срывает cutoff независимо от ML-шума |
| **M1-03** | Оценивать вероятность пропуска отправления | Доля исторических ошибок прогноза, при которых готовность уходит за cutoff планового рейса (`routing.planned_cutoff`); документы после cutoff дают 1; risk `low <0.35`, `medium <0.7`, иначе `high`; вероятность синтетическая, не гарантированная | `Prediction.miss_probability`, `risk` | `tests/test_predictive.py`; значения воспроизводимы при seed 42 |
| **M1-04** | Объяснять риск, а не выдавать «чёрный ящик» | Детерминированные короткие факторы по входным эффектам; не выдаются за SHAP | `Prediction.factors` | Факторы меняются при сценарии и согласуются с входными признаками |

| **M1-06** | Видеть узкие места хаба заранее | `hubs.py`: почасовой спрос и мощность каждого узла на 72 ч, синтетический фон + текущие маршруты демо-перевозок, окна при загрузке ≥ 0,85; сценарий запрошенной перевозки применяется как региональное условие (у Махачкалы) | `GET /api/hubs/forecast?shipment_id=…`; UI: слой «Загрузка узлов», слайдер, карточка «Узкие места · 72 ч» | `tests/test_hubs.py`; фон помечен синтетическим |
| **M2-01** | Подготовить сведения и документы до прибытия | `preclearance.py`: декларация, три вида документов, версии | `PUT/GET /api/shipments/{id}/preclearance`; `DeclarationInput`, `Declaration` | `tests/test_preclearance.py`; сохраняется черновик даже при бизнес-ошибке |
| **M2-02** | Проверять комплектность и расхождения | Проверки: непустые поля, страна из двух букв, HS 6–10 цифр, три разных документа, совпадение контейнера и массы ≤1 кг | Коды `required`, `invalid_format`, `missing_document`, `duplicate_document`, `mass_mismatch`, `container_mismatch`; `POST .../validate` | Демо: масса 19 000 вместо 20 000 даёт `validation_failed` и точное поле |
| **M2-03** | Разграничить роли и защитить изменения | Токен определяет роль; actor создаётся сервером, не берётся из JSON | Broker: save/validate/submit; reviewer: только review; `401/403` | `tests/test_api.py`; токены — demo-secrets, привязка к localhost |
| **M2-04** | Версионировать документы и статусы | Одна декларация на отправку; save увеличивает версию; принятые правки создают новый черновик и отменяют `accepted` | Статусы `draft`, `validation_failed`, `ready`, `submitted`, `auto_accepted`, `accepted`, `needs_revision` | `tests/test_preclearance.py`; submit разрешён только из `ready` |
| **M2-05** | Идемпотентность повторной подачи | Транзакционно хранится `(actor.id, shipment_id, key)` + версия/хеш/ответ; replay проверяется до проверки состояния | `POST .../submit`, обязательный `Idempotency-Key`; отсутствие → `422`; конфликт версии → `409` | Повтор с тем же ключом возвращает исходный ответ без новой записи аудита |

| **M2-07** | Не имитировать таможенный выпуск | Только локальный demo-контур и статусы `auto_accepted` (демо-правила) / `accepted`; внешний таможенный шлюз не подключён, UI явно объясняет demo-only | `ReviewRequest`: `accepted` или `needs_revision` | `tests/test_demo.py`; в интерфейсе нет статуса таможенного выпуска и заявления о выпуске |
| **M3-01** | Единое окно с цифровым двойником груза | `frontend/**`: dashboard, карточка груза, карта/схема, timeline | `GET /api/dashboard`, `GET /api/shipments/{id}`; `ShipmentDetail`, `Event` | План, прогноз и факт визуально разделены; загрузка/ошибка/пустые альтернативы обработаны |

## 3. Сценарий приёмки

1. Dashboard: SCT-001…006 (004–006 — восточная ветка), метка `synthetic`, сводка.
2. SCT-001: план прибытия 10:00Z, cutoff 14:00Z, отправление 18:00Z; прогноз готовности до cutoff (≈ 11:35Z).
3. `storm`: прибытие +3 ч, очередь +2 ч, ветер 22 м/с, волна 4,5 м; готовность после cutoff; текущий маршрут infeasible, `missed_connection=true`.
4. Слой «Загрузка узлов»: окно перегрузки у Махачкалы. Восстановление на следующем отправлении, альтернативы через Олю и Амирабад (последняя доступна и при «Закрытие»); сравнение ETA/цены/CO₂; выбор допустимого варианта.
5. Pre-clearance: предзаполненная декларация → `ready` → submit с ключом → `auto_accepted` (R1–R5); ошибка массы → `validation_failed`; недоверенный отправитель → `submitted` → `accepted` проверяющим; повтор с тем же ключом без дубля аудита; verify + реестр 3 из 3.
6. Reset: базовый прогноз возвращается, выбор маршрута очищается, документы и аудит остаются.

Команды: `./scripts/check.sh` для проверки, `docker compose up -d --build` или `./scripts/dev.sh` для показа. Подробный тайминг — в `docs/DEMO.md`.

## 4. Честные ограничения

| Область | Что сделано | Что не заявляем |
|---|---|---|
| История | Синтетический генератор с нелинейными эффектами погоды/очереди, seed 42 | Реальную историю портов Каспия и подтверждённую точность модели |
| Погода | Синтетика по умолчанию; опциональный кэш Open-Meteo с source/freshness, не обязателен для демо | Навигационный прогноз, покрытие всего Каспия, «live» без кэша |
| AIS | Не подключён | Реальные позиции судов или live-карту |
| Расписания и узлы | Иллюстративные сервисы, координаты, вместимость, стоимость | Наличие реальных рейсов, мест, паромов и таможенных правил |
| Маршруты | Локальная симуляция выбора по расписанию | Реальное бронирование, резервирование вместимости, договор перевозки |
| ESG | `v1`, только оставшиеся участки, 3 моды | WTW, GLEC/ISO-сертификацию, учёт терминалов/хранения/порожних пробегов |
| Pre-clearance | Локальный SQLite, роли demo, тестовые статусы, идемпотентность, аудит | Интеграцию с ФТС/таможней, юридический выпуск, production tenant isolation |
| Аудит | Hash-chain из SHA256 канонического JSON (HMAC при `AUDIT_HMAC_KEY`) | Электронную подпись, внешний trust anchor, доказательство юридической силы или достоверности документа |
| Загрузка узлов | Синтетический фон и демо-масштаб мощностей, модель очереди — упрощённая | Реальные данные терминалов, подтверждённую точность прогноза загрузки |
| Доступ | Demo bearer-токены, localhost | Production identity/security, SLA, соответствие требованиям регулятора |
| Реестр и «смарт-контракт» | Прототип: 3 узла-свидетеля в одном процессе, HMAC, кворум 2 из 3; детерминированный набор правил `rules-v1` с хешем | Блокчейн-сеть, консенсус между независимыми операторами, асимметричные подписи, юридическую силу автоматического решения |

## 5. Границы MVP

В обязательный результат не входят: live AIS, Neo4j, внешний LLM-агент, 3D-визуализация, собственная блокчейн-сеть, десятки интеграций и глобальная оптимизация всего Каспия. Это возможные направления развития, а не выполненные требования.
