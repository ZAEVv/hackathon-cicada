# Smart Caspian Transit — финальный питч

Кейс 2 «Предиктивный цифровой двойник мультимодального хаба», трек «Цифровая экосистема МТК
Север–Юг». Цифр достигнутой экономии нет сознательно: всё про эффект — гипотезы для пилота.

## 1. Проблема

Стыковка теряется не на карте, а во времени. Цепочка ж/д терминал → российский порт → море →
иранский порт → авто срывается, когда груз или документы готовы позже окончания приёма.
Трекер фиксирует задержку постфактум; узкое место в порту видно, когда очередь уже стоит;
документы проверяются вручную в последний момент.

## 2. Решение

Цифровой двойник перевозки и упрощённый двойник хабов в одной цепочке:
событие (шторм / очередь / закрытие) → прогноз готовности и риска пропуска → прогноз загрузки
узлов на 72 ч → допустимые альтернативы с ETA, стоимостью и CO₂e → выбор → предварительное
оформление документов по правилам → проверяемый журнал.

## 3. Что реализовано (работает в демо)

| Модуль ТЗ | Что есть |
|---|---|
| M1. Предиктивная модель | Монотонный Gradient Boosting `gbm-v4` против baseline на временном разделении; признаки — очередь, ветер, осадки, известная задержка, масса, **высота волны**; вероятность пропуска и факторы риска; почасовой прогноз загрузки узлов на 72 ч с окнами узких мест |
| M2. Цифровой коридор / «смарт-контракт» | Декларация с версиями и проверками (масса, контейнер, документы); набор правил **`rules-v1`** (R1–R5) с хешем — при выполнении всех правил статус «Одобрена автоматически», иначе ручное рассмотрение отдельной ролью; идемпотентная отправка; хеш-цепочка аудита; **прототип реестра** — три узла-свидетеля (таможня РФ, таможня Ирана, оператор порта) подписывают голову цепочки, кворум 2 из 3; защищённое API с ролями и лимитами |
| M3. Единое окно логиста | Карта западной линии и восточной ветки (Актау / Туркменбаши / Амирабад), хронология план / прогноз / факт, слой «Загрузка узлов», альтернативы с ETA / $ / CO₂e и выбором, страница «Сводка» (тоннаж по неделям, KPI) |

Что видно в демо (синтетика, seed 42): «Шторм» на SCT-001 (ветер 22 м/с, волна 4,5 м) переводит
риск в «Высокий», готовность уходит за дедлайн, Махачкала становится узким местом с пиком ≈ 165 %;
«Закрытие» линии даёт альтернативы через Олю (быстрее) и Амирабад (≈ 445 кг CO₂e против 1 613);
декларация с демо-значениями проходит правила за три клика. MAE модели 1,51 ч против 5,02 ч у
baseline, ROC AUC 0,90 на отложенной синтетической выборке с ненаблюдаемыми инцидентами (поломки
кранов, досмотры, сдвиг отхода судна). Текущая погода — живая из Open-Meteo (ветер, осадки, волна)
с подписью источника и резервом на синтетику. Запуск: `docker compose up -d --build`.

## 4. Честные границы

- Данные синтетические: история, расписания, вместимость, стоимость (погода — живая Open-Meteo,
  при сбое — синтетика). AIS нет. Метрики (AUC 0,90, MAE 1,51 ч) — на синтетике, не на реальных
  рейсах.
- Прогноз узлов: синтетический фон + демо-перевозки, мощности демо-масштаба.
- «Одобрена автоматически» и «Принята» — не таможенный выпуск; правила и списки выдуманы
  для демо; внешнего таможенного шлюза нет.
- Реестр — прототип: три узла — отдельные сетевые сервисы (свои контейнеры, тома, ключи, подписанные
  запросы), но все у одного оператора на одном хосте; симметричный HMAC, проверяющий знает все ключи,
  BFT-консенсуса нет. Он показывает схему (кворум 2 из 3, отказ узла, отказ от неупорядоченных записей,
  обнаружение переписанной истории), но не защищает от владельца хоста.
- ESG: коэффициенты `v1`, только оставшиеся участки, не GLEC/ISO.
- Выбор маршрута — симуляция, не бронирование. Доступ — демо-токены на localhost.

## 5. Следующие шаги

1. **Пилот на одном коридоре:** read-only события от терминала и перевозчика, переобучение модели
   на реальной истории, измерение KPI против baseline (доля пропущенных стыковок, часы простоя,
   перебронирования, время подготовки документов).
2. **Реестр между участниками:** узлы у таможен и порта на своей инфраструктуре, асимметричные
   подписи (Ed25519), правила оформления согласованы участниками и закреплены версией.
3. **Таможенный контур:** тестовый шлюз, юридическая модель обмена; реальный выпуск — только после
   соглашений и аттестации.
4. **Промышленный контур:** PostgreSQL, OAuth2/mTLS, очереди, мониторинг дрейфа модели, SLA.

Кто платит (гипотеза): экспедитор/брокер — за рабочее место и оформление, порт — за прозрачность
очереди, перевозчик — за видимость стыковок. Цена — после пилота.

**Что просим:** тестовые API порта/перевозчика, пилотного партнёра на одном коридоре и экспертизу
по таможенному контуру.
