# Кейс 2 «Smart Caspian Transit» — разбор ТЗ, решения, подзадачи, агенты и модели

Трек 3 · Цифровая экосистема МТК «Север-Юг». Предиктивный цифровой двойник мультимодального хаба.

---

## 1. Что на самом деле просят

Из ТЗ три обязательных модуля MVP:

| # | Модуль | Что должно быть на защите |
|---|--------|---------------------------|
| M1 | Предиктивная модель | Прогноз задержки мультимодальной стыковки (ж/д состав ↔ паромная переправа, порт) по истории, погоде на Каспии и загрузке портов. Должен быть **предсказание узкого места до его появления**. |
| M2 | «Смарт-контракт / Цифровой коридор» | Прототип **pre-clearance** (предварительного таможенного оформления) через распределённый реестр **или** защищённые API. Блокчейн помечен как «опционально». |
| M3 | «Единое окно логиста» | Интерфейс: вместо трек-номера — **цифровой двойник груза**, расчёт **углеродного следа (ESG)** и **альтернативные маршруты** при форс-мажоре. |

Скрытые требования, которые судьи почти наверняка проверят:
- **Сквозной сценарий**: груз → событие (шторм / очередь в порту / таможня) → прогноз → алерт → альтернативный маршрут → пересчёт ETA и CO₂. Без демо этого сценария остальное не засчитают.
- **Концепция + прототип**. Задача формулируется как «концепция и прототип», значит нужна архитектура и отдельный документ на 3–5 слайдов про экономику и интеграцию (кто платит, кто подключается, как стыковаться с ФТС/таможнями/ТЭО).
- **Интеграции** («API-интеграции» в стеке): хватит 2–3 реальных внешних источника (погода, AIS) плюс собственный API для таможни. Остальное — мок с честной пометкой.
- **Данных по Каспию в открытом доступе почти нет.** Команды, которые это понимают и честно говорят «исторические данные портов синтетические, модель обучена на сгенерированном датасете с реальными распределениями из открытых источников», выигрывают у тех, кто делает вид, что у них есть реальные данные.

## 2. Что уже сделано другими (референсы)

Нашёл несколько реальных кейсов и источников. Важно: **готового open-source решения именно под этот кейс не найдено** — значит идея не «уже решена», а у вас есть пространство для сборки.

1. **Север–Юг (INSTC) и диагностика проблем.** Отчёт Всемирного банка по коридору «Middle Trade and Transport Corridor» (2023): главная причина задержек — морские участки при избытке портовых мощностей; много бумажной работы; фрагментированная цифровизация портов и ж/д границ; слабая видимость грузов в пути. Пробная отправка в Астрахань и Баку шла 43 дня вместо ожидаемых, Каспийский переход — 8 дней вместо 4. Источник: [World Bank MTTC report](https://thedocs.worldbank.org/en/doc/6248f697aed4be0f770d319dcaa4ca52-0080062023/original/Middle-Trade-and-Transport-Corridor-World-Bank-FINAL.pdf). **Использовать в презентации как обоснование проблемы.**
   - Мелководье северного Каспия у Оли/Астрахани ограничивает вместимость судов (по [Caliber.az](https://caliber.az/en/post/why-azerbaijan-is-a-reliable-partner-in-the-north-south-corridor)). Это хорошая фича для модели: «осадка/уровень воды» как фактор.
   - Анзали подключён к ж/д с июня 2024; линия Анзали–Астара ещё строится ([Wikipedia: Caspian Port](https://en.wikipedia.org/wiki/Caspian_Port)). Для демо берите Махачкала/Астрахань/Анзали/Амирабад как узлы графа.
   - Важный контекст: по [Maritime Executive](https://maritime-executive.com/article/centcom-mirrors-naval-blockade-with-iron-gate-for-iran-s-borders) и [IranWire](https://iranwire.com/en/features/160084-beyond-the-naval-siege-how-the-us-iron-gate-strategy-aims-to-choke-irans-trade) на текущий момент есть геополитические ограничения на южный Каспий. **Это не должно ломать модель, но сделайте сценарий «геополитический риск» как отдельный тип события в графе** — это выглядит зрело и попадает в тему «форс-мажор».

2. **TradeLens (Maersk + IBM) — главный урок для M2.** Блокчейн-платформа для eBL. Пилот с таможней Саудовской Аравии (FASAH) был положительным, но проект закрыли. Причины по анализам: слабый бизнес-кейс, сложность стандартизации таможни между странами, параллельная китайская GSBN, отсутствие нейтрального управления. Источники: [digitalizetrade](https://www.digitalizetrade.org/node/221), [Why TradeLens failed](https://wisechainconsult.substack.com/p/8-why-did-tradelens-failed-and-and), [Saudi customs pilot (FreightWaves)](https://www.freightwaves.com/news/saudi-customs-pilots-shipment-movement-via-blockchain).
   - **Вывод для вас:** не строить реальный блокчейн-консорциум. Сделать **API + подписанные документы (Ed25519/JWS) + хеш-цепочка событий (append-only лог)**. Это даёт ту же гарантию целостности и защиты, но без «ещё одной сети, которую никто не подключит». На защите: «блокчейн не нужен — нужна единая схема данных и нейтральный узел; мы показываем, как это ляжет на распределённый реестр в будущем».

3. **Граф логистики (Neo4j).** Neo4j публикует туториалы и кейсы по трекингу груза как графу событий (Cargo 2000), по средним эффективным временам по ногам маршрута и по what-if сценариям (альтернативные пути при отказе). Источники: [GDS Part 3 — pathfinding & what-if](https://neo4j.com/blog/developer/gds-supply-chain-pathfinding-optimization/), [Neo4j supply chain](https://neo4j.com/videos/how-knowledge-graphs-help-you-build-a-more-resilient-supply-chain/). Это **официальный паттерн для M3 (альтернативные маршруты) и для «цифрового двойника» как графа**. Предсказательной ETA-модели там нет — её нужно строить самим (граф-фичи + GBM). Метавертный кейс про ETA на графах — вторичный источник, не проверен первоисточником.

4. **ESG / углеродный след — GLEC и ISO 14083.** GLEC Framework v3.x (актуальная версия v3.2, октябрь 2025) — практический стандарт поверх ISO 14083:2023. Считать надо well-to-wheel: операционные + upstream-выбросы. API-аналоги, которые можно сравнить с вашим калькулятором: [Climatiq Freight API](https://climatiq.io/blog/introducing-freight-v2), [Dcycle Logistics API](https://code.dcycle.io/guides/emissions/glec-tutorial.md), [Searoutes](https://searoutes.com/en/blog/glec-framework-2025-the-ultimate-guide-to-iso-14083-sustainable-logistics). **Важно:** не заявляйте «соответствие ISO 14083», если не выполнены все процедуры. Пишите «методика на основе GLEC v3, коэффициенты-заглушки, требуется верификация».

5. **Хакатон-аналоги.** [Culltron Smart Port Flow](https://lablab.ai/ai-hackathons/amd-developer/culltron/culltron-smart-port-flow) (AMD hackathon) — почти та же идея: AI-агент для портов, предсказание задержек и эмиссий, сценарный симулятор. Смотрите его, чтобы не скопировать концепцию один в один и понимать, что уже «видели» жюри. ChainPORT (Антверпен, 2018) — студенты предсказывали ETA по погоде через API. Port digital twin в научных работах: модели LSTM/Random Forest/GBM для задержек в портах. [Пример статьи](https://www.researchgate.net/publication/408206898_Artificial_intelligence-enabled_digital_twins_for_sustainable_and_carbon-neutral_smart_port_operations) — цифра 92.3% там неоднозначно описана, **не цитируйте без проверки**.

6. **Данные, которые реально можно взять:**
   - Погода и морские прогнозы: Open-Meteo (бесплатно, без ключа; есть marine-модель с волнами).
   - AIS: aisstream.io (бесплатный ключ, WebSocket) — для живой картины судов в Каспии; либо синтетика.
   - Порты, ж/д, таможня: **синтетика**, но генератор должен использовать реальные координаты портов и реалистичные распределения задержек (с обоснованием в README).
   - Уровень Каспия: публичные ряды (например, данные по уровню моря из открытых источников) — как фича сезонности.

## 3. Архитектура решения (рекомендация)

```
[Источники]                 [Ingestion]           [Хранилище/граф]
Open-Meteo (погода/волны) ─┐
AIS (aisstream / синтетика)├─► ingestion svc ─► Neo4j (или NetworkX в хаке)
Синтетика: порты, ж/д,     │   (очереди, кэш)     узлы: Shipment, Leg, Port,
  таможня, загрузка ──────┘                       Terminal, Vehicle, WeatherEvent,
                                                  GeoRiskEvent
                                       │
        ┌──────────────────────────────┼───────────────────────────────┐
        ▼                              ▼                               ▼
 [M1 Predictive]               [M2 Pre-clearance API]          [M3 Route + ESG]
 GBM (LightGBM) по легам,       FastAPI, статусы, подписанные    Pathfinding по графу
 квантильный прогноз,           документы (Ed25519/JWS),         (cost = время + цена
 опц. LSTM на ряды              append-only лог с хешами,        + CO₂ + риск),
 → P(задержки>X ч),             мок-эндпоинты ФТС/таможни        GLEC-калькулятор
   узкие места по портам                                         (well-to-wheel)
        │                              │                               │
        └──────────────────────────────┴───────────────┬───────────────┘
                                                       ▼
                                      [Frontend: Единое окно логиста]
                                      карта (MapLibre/Leaflet), digital twin
                                      груза (timeline ног), алерты, ESG, альтернативы
                                                       │
                                      [Опц. runtime-агенты (OpenAI/Claude)]
                                      объясняют алерт и предлагают действие
```

Ключевые решения, которые стоит зафиксировать в первый час хакатона:
- **Единая модель данных**: Shipment / Leg / Port / Event / Forecast. Всё остальное — производные. Без этого агенты разъедутся.
- **Один сценарий демо**: «шторм на Каспии → задержка паромной стыковки Махачкала → прогноз + алерт → альтернативный маршрут через Астрахань/Анзали → пересчёт ETA и CO₂».
- **Прогноз — вероятностный**: не «будет задержка», а «P(задержка > 6 ч) = 0.72» + главный фактор (SHAP или просто важность фич). Это сильнее для жюри и честнее.

## 4. Подзадачи и чеклист по пунктам

### P0 — без этого не защищаться
- [ ] Модель данных и JSON-схемы (Shipment, Leg, Port, Event, Forecast, Route)
- [ ] Генератор синтетики: 8–10 узлов (Астрахань, Махачкала, Оля, Анзали, Амирабад, Актау, Баку, Туркменбаши и т.п.), 3–6 месяцев истории, сезонность, штормы
- [ ] Интеграция Open-Meteo (погода + волны) и кэш
- [ ] M1: baseline (среднее/медиана по историческим задержкам) → GBM, метрики MAE / ROC-AUC на отложенной выборке, квантили
- [ ] M3-core: граф узлов и ног, поиск альтернативного маршрута (кратчайший по сумме весов), пересчёт ETA
- [ ] M3-ESG: калькулятор CO₂ по ногам (мода × расстояние × коэффициент) с источником коэффициентов
- [ ] Фронт: карта, список грузов, карточка «двойника» (timeline ног), блок алертов, блок ESG и альтернатив
- [ ] Сценарный переключатель «шторм / очередь / геориск» для демо
- [ ] Сквозной скрипт демо (одна команда → сценарий работает) и README

### P1 — сильно повышает оценку
- [ ] M2: FastAPI pre-clearance — создание декларации, загрузка документов, статусы, подпись JWS, хеш-цепочка событий, проверка целостности эндпоинтом `/verify`
- [ ] Моки ФТС/таможенного API с реалистичными ответами и ошибками (таймауты, отказ, повторная отправка)
- [ ] AIS-поток (aisstream) или синтетические позиции судов на карте
- [ ] Объяснимость прогноза (важность фич, топ-3 фактора на алерт)
- [ ] Runtime-агент, который по алерту формирует рекомендацию (через tools: найти маршрут, посчитать CO₂, создать pre-clearance)

### P2 — «wow», если останется время
- [ ] Neo4j вместо NetworkX + Cypher-запросы в демо
- [ ] Сравнение с API Climatiq/Dcycle (проверка порядка величин CO₂)
- [ ] Бумага/слайд: экономика, кто подключается (операторы портов, ж/д, брокеры, ФТС), путь интеграции
- [ ] Симуляция «что если» (ускорить таможню на 2 ч → сколько сэкономится по ETA)

### Документы для защиты (обязательно)
- Концепция на 1 слайд: проблема (цифры ВБ) → решение → сценарий → отличие от TradeLens
- Архитектурная схема
- Метрики модели, честно указать, что данные синтетические
- Что не сделано и почему (блокчейн — намеренно заменён на подписанный журнал)

## 5. Как распределить cloud-агентов

Главный принцип: **агенты работают параллельно только по contract-first**. Сначала лид фиксирует контракты (JSON-схемы, OpenAPI, фикстуры данных), потом все пишут код против них. Каждый агент — отдельная ветка/worktree, мерж только через лида.

| Агент | Зона ответственности | Файлы/пакеты | Вход | Выход |
|---|---|---|---|---|
| **A0 Lead / Orchestrator** | Контракты, план, интеграция, мерж, финальный ревью | `contracts/`, `docs/`, `integration/` | ТЗ | Схемы, мерж, сводный отчёт |
| **A1 Data** | Синтетический генератор, ingestion, Open-Meteo, AIS | `data/`, `ingestion/` | схемы | `fixtures/*.parquet/csv`, сервис ингестии |
| **A2 Predictive** | M1: baseline, GBM, квантили, объяснимость | `ml/` | fixtures | `models/*.pkl`, `predict()` API, метрики |
| **A3 Graph & Routing** | Граф, pathfinding, ETA-пересчёт, сценарии | `graph/` | схемы, fixtures | `route_alternatives()`, Cypher/NetworkX |
| **A4 Pre-clearance API** | M2: FastAPI, подпись, журнал, моки таможни | `api/` | OpenAPI | Работающий сервис + тесты |
| **A5 ESG** | GLEC-калькулятор, коэффициенты, тесты, описание методики | `esg/` | схемы | `co2_for_route()` + таблица коэффициентов с источниками |
| **A6 Frontend** | Единое окно: карта, двойник, алерты, ESG | `web/` | OpenAPI + mock JSON | Работающий UI на моках → на реальном API |
| **A7 QA / Reviewer** | Тесты, линт, сквозной сценарий, ревью чужих PR | `tests/`, CI | всё | Отчёт: что падает, что не покрыто |

Запуск по волнам:
- **Волна 0 (лид, 30–60 мин):** схемы, OpenAPI, фикстуры-заглушки, сценарий демо.
- **Волна 1 (параллельно):** A1, A2, A3, A4, A5, A6 (A6 на моках).
- **Волна 2:** интеграция, A6 переключается на реальный API, A7 гоняет сквозной сценарий.
- **Волна 3:** полировка, слайды, демо-скрипт, репетиция.

Почему так режем: A5 (ESG) и A4 (API) — почти независимы и небольшие; A2 (ML) — самая «тяжёлая» часть по качеству решений, ему нужен лучший ум; A6 можно вести на моках полностью отдельно. Конфликты файлов исключены, потому что у каждого агента свой пакет.

## 6. Какая модель на что

Модели OpenAI в этом задании участвуют. Имена моделей OpenAI я не смог однозначно подтвердить с официальной страницы (поиск дал противоречивые данные от сторонних блогов), поэтому **перед запуском сверьте актуальные ID в консоли OpenAI**. Ниже — по классам.

| Задача | Рекомендуемый класс | Модель (Claude) | Модель (OpenAI) |
|---|---|---|---|
| Лид, архитектура, контракты, ревью интеграции | Самый сильный | Opus 5.5 (для самых трудных архитектурных решений — Fable 5.2, если доступна) | Flagship-reasoning (GPT-6.x Astra/Sol класс) как второе мнение |
| ML-код, метрики, выбор признаков (A2) | Сильный, аккуратный в математике | Opus 5.5 или Sonnet 5.5 | Reasoning-модель среднего класса |
| Граф, маршруты, API, фронт (A3, A4, A6) | Рабочая лошадка для кода | Sonnet 5.5 | Mid-tier GPT-6.1 класса (код/агентные задачи) |
| ESG-калькулятор, тесты, генерация фикстур, документация (A5, A7 мелочи) | Дешёвый, быстрый, детерминированный | Haiku 5.5 | Low-cost tier (GPT-6 Luna класса) |
| Кросс-ревью (второй взгляд на код другой семьёй моделей) | Сильный, из **другой** семьи | — | Flagship reasoning |
| Runtime-агент в продукте (объяснение алертов, рекомендация) | Дешёвый и быстрый на каждый запрос | Haiku 5.5 или Sonnet 5.5 | Low/mid-tier + function calling |

Правило: **лид и ревьюер должны быть из разных семей** (Claude пишет, OpenAI ревьюит, или наоборот) — меньше общих слепых пятен.

Цены по OpenAI из источников противоречивы (разные блоги указывают разные ставки для одних и тех же моделей), поэтому бюджет считайте по тарифам из вашего аккаунта, а не по сторонним таблицам.

## 7. Оркестрация

Два уровня, не путайте их:

### Уровень 1 — dev-оркестрация (как строите проект)
1. Лид создаёт `contracts/` и `docs/plan.md`, фиксирует интерфейсы.
2. Для каждого агента — отдельная cloud-сессия/worktree с коротким брифом: «пакет X, входы Y, выход Z, критерий готовности».
3. Агенты пушат в свои ветки и открывают PR в main.
4. A7 (QA) прогоняет тесты на каждом PR; отдельный ревьюер из другой семьи моделей проверяет.
5. Лид мержит по порядку зависимостей (данные → модели/граф → API → фронт → демо).
6. Раз в час — короткий статус лиду: что готово, что блокирует.

Пример конфига плана (можно вести в файле `docs/orchestration.yaml`, чтобы лид и агенты читали один источник правды):

```yaml
project: smart-caspian-transit
contracts:
  - contracts/shipment.schema.json
  - contracts/leg.schema.json
  - contracts/forecast.schema.json
  - api/openapi.yaml
agents:
  A1_data:      { model: sonnet-5.5, scope: [data/, ingestion/], deps: [contracts] }
  A2_predict:   { model: opus-5.5,   scope: [ml/],               deps: [A1_data] }
  A3_graph:     { model: sonnet-5.5, scope: [graph/],            deps: [A1_data] }
  A4_api:       { model: gpt-6.1-mid, scope: [api/],             deps: [contracts] }
  A5_esg:       { model: haiku-5.5,  scope: [esg/],              deps: [contracts] }
  A6_web:       { model: sonnet-5.5, scope: [web/],              deps: [api/openapi.yaml] }
```

### Уровень 2 — runtime-оркестрация (что работает в самом продукте)
Если в продукте нужны агенты, делайте **не «чат с 10 ботами»**, а 3–4 инструмента, которые вызывает один оркестратор:
- `forecast_delay(leg_id, horizon_h)` → вызывает модель M1
- `find_alternatives(shipment_id)` → M3 граф
- `compute_co2(route)` → M3 ESG
- `start_precleared(shipment_id)` → M2 API

Оркестратор — один LLM-цикл с function calling (OpenAI Agents SDK или Claude tool use). Он получает алерт, вызывает инструменты в нужном порядке и формирует текст для логиста. Жёсткие правила вынести в код (статус-машина pre-clearance), а LLM — только в объяснения и выбор действия. Это защищает от галлюцинаций в «юридически значимых» шагах.
