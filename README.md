# Smart Caspian Transit

Рабочий прототип кейса 2 «Предиктивный цифровой двойник мультимодального хаба» (трек «Цифровая
экосистема МТК Север–Юг»): прогноз стыковок и загрузки узлов, цифровой коридор pre-clearance и
единое окно логиста. Все данные синтетические.

Полный разбор устройства проекта и ответы на вопросы жюри: [docs/PROJECT_GUIDE_RU.md](docs/PROJECT_GUIDE_RU.md).

Как мы это делали, что выучить к защите и презентация: [docs/HOW_WE_BUILT_RU.md](docs/HOW_WE_BUILT_RU.md), [docs/presentation/](docs/presentation/) (PDF, HTML и текст выступления).

## Запуск

### Docker (рекомендуется для показа)

```bash
docker compose up -d --build
```

Интерфейс: http://127.0.0.1:5173. Один контейнер, два процесса: API слушает только loopback
контейнера (`127.0.0.1:8000`), наружу опубликован только UI (`vite preview`), который проксирует
`/api`. Порт публикуется на `127.0.0.1` хоста. Проверка: `curl http://127.0.0.1:5173/api/health`.
Контейнер работает от непривилегированного пользователя, с `read_only`, `cap_drop: ALL`;
SQLite лежит в томе `caspian-data` (сброс чистой БД: `docker compose down -v`).
Рядом поднимаются три узла реестра `witness-1..3` (тот же образ, команда
`python -m backend.app.witness_node`): у каждого свой том, они в отдельной внутренней сети
`ledger` без опубликованных портов и без выхода наружу, с тем же hardening и healthcheck.
Опциональные переменные (`BROKER_TOKEN`, `REVIEWER_TOKEN`, `DISABLE_DEFAULT_TOKENS`,
`ENABLE_API_DOCS`, `AUDIT_HMAC_KEY`, `LEDGER_WITNESS_KEYS`, `LEDGER_WITNESS_URLS`, `WEATHER_PROVIDER`) передаются из окружения или `.env` рядом с `docker-compose.yml`.
Рядом поднимается сервис `graph` (Neo4j 5 Community, heap 512 МБ + page cache 128 МБ, том
`caspian-graph`, порты наружу не публикуются); `app` ждёт его healthcheck. Пароль —
`GRAPH_DB_PASSWORD` (по умолчанию локальный `caspian-graph-local`), см. «Граф коридора».

### Без Docker

Нужны Python 3.11+ и Node.js 20+ с npm.

```bash
./scripts/dev.sh
```

Интерфейс: http://127.0.0.1:5173 · API: http://127.0.0.1:8000/api/health
(OpenAPI `/docs` выключен по умолчанию, включается `ENABLE_API_DOCS=1`).

Зависимости: `requirements.txt` — только runtime, `requirements-dev.txt` — плюс pytest/httpx
для тестов (`dev.sh` ставит его). Локальные настройки: `cp .env.example .env`, см. «Безопасность».
Автоматический сквозной сценарий при запущенном API: `.venv/bin/python scripts/demo.py`
(по умолчанию `http://127.0.0.1:8000`; для Docker — `--base-url http://127.0.0.1:5173` или
`SCT_BASE_URL=...`). Печатает PASS/FAIL по каждой проверке, при ошибке код выхода ≠ 0.
Пошаговый сценарий показа на 5–7 минут — `docs/DEMO.md`.

## Что делает прототип

Каталог (синтетический): западная линия Астрахань (ж/д терминал) → Махачкала / Оля → Энзели →
Тегеран и восточная ветка Актау, Туркменбаши, Амирабад (сервисы `rail-east`, `sea-aktau`,
`rail-kz-tm`, `sea-tkm`, `sea-mak-amirabad`, `rail-amirabad`). Шесть перевозок SCT-001…SCT-006;
SCT-004…006 идут по восточной ветке.

Сквозной сценарий: событие («Шторм» / «Очередь» / «Закрытие») → прогноз готовности и риск
пропуска стыковки → прогноз загрузки узлов на 72 ч и узкие места → допустимые альтернативы с ETA,
стоимостью и CO₂e → выбор маршрута → предварительная декларация → тестовое решение → аудит.

### Цифровой коридор: правила, аудит, реестр

- **Предзаполненная декларация.** Новая декларация открывается с демо-значениями (отправитель
  «ООО «Волга Экспорт»», HS 847990, страна RU, документы `INV-/PL-/CMR-<id>`, масса и контейнер
  перевозки), поэтому основной путь — три действия: «Сохранить черновик» → «Проверить» → «Отправить».
- **Набор правил `rules-v1`** (`preclearance.py`) — детерминированная проверка при отправке:
  R1 документы согласованы с декларацией (контейнер, массы ±1 кг); R2 код ТН ВЭД не из списка
  ручного контроля (префиксы 93, 2844, 3601–3604); R3 стоимость за кг в диапазоне 0,05–500 $;
  R4 отправитель в списке доверенных (ООО «Волга Экспорт» / ТОО «Степь Экспорт» / Persian Caspian Export); R5 страна
  происхождения из списка (RU, KZ, IR, AZ, TM, UZ). Все пять пройдены → статус `auto_accepted`
  («Одобрена автоматически»); иначе `submitted` («На рассмотрении») и решение отдельной роли
  проверяющего. Решение, id и SHA-256 хеш набора правил (`ruleset_hash`) записываются в запись
  аудита `submit`; определение правил — `GET /api/preclearance/ruleset`. Списки и пороги
  иллюстративны, это не таможенные правила.
- **Хеш-цепочка аудита**: каждая операция — запись с `previous_hash` и SHA-256 (или HMAC при
  `AUDIT_HMAC_KEY`); `GET …/audit/verify` проверяет порядок, связи и соответствие текущей декларации.
- **Прототип распределённого реестра** (`ledger.py`, `witness_node.py`): три узла-свидетеля
  `witness-1`, `witness-2`, `witness-3` (в UI — «Таможня», «Порт», «Перевозчик»), у каждого своя
  SQLite и свой HMAC-ключ. В Docker это **три отдельных сетевых сервиса** в своих контейнерах; API
  обращается к ним по HTTP параллельно, с коротким таймаутом. Каждый запрос подписан HMAC
  (ключ узла, метка времени, одноразовый nonce), без подписи узел отказывает (401); ответ узла
  тоже подписан и привязан к nonce запроса, поэтому подменённый в пути ответ отбрасывается.
  Без `LEDGER_WITNESS_URLS` (тесты, `dev.sh`) те же узлы работают в процессе API, каждый в своём
  файле `<db>.witness-<id>.sqlite3`. После каждой записи аудита
  узлы принимают только продолжение своей цепочки (следующий номер и верный `previous_hash`) и
  подписывают `(shipment_id, sequence, hash, previous_hash, at)`; запись «закреплена» при 2 из 3.
  Сверка (`GET …/ledger` и блок `ledger` в `…/audit/verify`) обнаруживает переписывание или
  удаление локальной истории после закрепления — даже если цепочка внутри основной БД
  пересчитана целиком. Честно: в compose все три узла запускает один оператор на одном хосте,
  ключи симметричные и по умолчанию детерминированные dev-ключи (`LEDGER_WITNESS_KEYS` для
  замены), проверяющий знает все ключи; узлы видят только хеши, а не содержание документов;
  консенсуса (BFT) нет — только кворум подписей 2 из 3. Это permissioned-реестр в миниатюре; для
  реальной независимости узлы должны держать разные участники с асимметричными подписями.

#### Демо отказа узлов реестра (Docker)

```bash
docker compose up -d --build
# UI: #/documents/SCT-001 → «Сохранить черновик» → строка «Распределённый реестр: 3 из 3 узлов
# подписали · кворум 2 из 3 достигнут», чипы «Таможня · подписал», «Порт · подписал», «Перевозчик · подписал»
docker compose stop witness-2
# «Сохранить черновик» ещё раз → запись закреплена (2 из 3), чип «Порт · недоступен»
docker compose stop witness-3
# «Сохранить черновик» → операция проходит, но «кворум 2 из 3 не достигнут · кворум недоступен»;
# «Проверить цепочку» — локальная цепочка цела, реестр: no_quorum
docker compose start witness-2 witness-3
# узлы снова в сети, но записи, пропущенные во время простоя, они не подписывают задним числом:
# «Порт · отстаёт», статус «последние записи не закреплены» — честно, без «досинхронизации»
```

Сброс реестра вместе с БД: `docker compose down -v`. Через API то же видно в
`GET /api/shipments/{id}/ledger` (`mode: "network"`, у каждого узла `state` и `error`:
`timeout` / `unreachable` / `rejected` / `bad_reply`).

### Метрики модели

Прогон на отложенной синтетической выборке (`gbm-v4`, seed 42; 576 строк обучения,
144 теста, граница разделения 2026-10-25T10:10:51Z): **MAE модели 1,51 ч против 5,02 ч у baseline**
(медиана train), **ROC AUC 0,90** для пропуска стыковки (55 пропусков из 144).

Синтетическая история намеренно содержит то, чего модель не видит: поломки кранов (4 % + 1 п.п.
на час очереди, +2–9 ч), выборочный досмотр (12 %, гамма-распределение, в среднем +1,8 ч),
разброс смен (σ 0,4 ч), гетероскедастичный шум (растёт с ветром и очередью, в шторм ×1,5) и сдвиг
фактического cutoff судна (σ 2 ч, иногда судно задерживают на 2–8 ч или закрывают приём раньше).
Бронирование делается заранее по «хорошей погоде» плюс запас, поэтому пропуски дают штормы и
инциденты. Поэтому идеальная метрика недостижима: если бы модель знала фактическую задержку,
AUC был бы ≈ 0,94; только по запасу времени — 0,85, только по прогнозу задержки — 0,83. На других
seed AUC 0,83–0,93. Это всё ещё синтетика, а не точность на реальных рейсах. Подробно:
`docs/PROJECT_GUIDE_RU.md`.

## Граф коридора (Neo4j)

Сеть коридора — это граф по своей природе: узлы (порты, терминалы) и расписанные сервисы между
ними, а вопрос маршрутизации — «какие цепочки сервисов ведут из A в B». Поэтому топология хранится
в графовой БД (Neo4j 5 Community, драйвер `neo4j`) и перебирается Cypher-запросом, а проверка
расписаний (cutoff, обработка, вместимость, тип груза) остаётся в Python (`routing._schedule`).

Модель (`backend/app/graphdb.py`):

```
(:Hub {id, name, country, lat, lon, kind})
  -[:SERVICE {id, mode, distance_km, duration_hours, departures[], cutoff_hours,
              handling_hours, capacity_tonnes, cost_usd, allowed_cargo[]}]->
(:Hub)
```

Сервис — связь, а не узел: у него ровно один пункт отправления и назначения, расписание — плоский
список ISO-времён (допустимое list-свойство), параллельные сервисы — параллельные связи, а путь из
`:SERVICE` сразу является цепочкой сервисов. Каталог загружается при старте API идемпотентно
(`MERGE` + удаление устаревших узлов и связей; ограничение уникальности `Hub.id`).

Запрос путей (при «Закрытии» заблокированные сервисы отсекаются в самом запросе):

```cypher
MATCH p = (o:Hub {id: $origin})-[:SERVICE*1..8]->(d:Hub {id: $destination})
WHERE none(r IN relationships(p) WHERE r.id IN $blocked)
  AND all(i IN range(0, size(nodes(p)) - 2) WHERE NOT nodes(p)[i] IN nodes(p)[i + 1..])
RETURN [r IN relationships(p) | r.id] AS service_ids
```

Например, Махачкала → Тегеран при закрытии `sea-main`: `[transfer-olya, sea-olya, road-final]` и
`[sea-mak-amirabad, rail-amirabad]`. Второй предикат требует простой путь (без повторного узла),
как `networkx.all_simple_paths`; предел 8 плеч не отсекает ни одного пути каталога (8 узлов).

Переменные: `GRAPH_DB_URL` (например `bolt://graph:7687`), `GRAPH_DB_USER` (`neo4j`),
`GRAPH_DB_PASSWORD`. **Резерв:** если `GRAPH_DB_URL` не задан или Neo4j недоступен при старте,
API пишет строку в лог и использует прежний in-memory `networkx`; если БД пропала во время работы,
запрос отвечается через `networkx` (лог), при восстановлении — снова через Neo4j. Активный бэкенд
виден в `GET /api/health` (`"graph_backend": "neo4j" | "networkx"`) и в строке источников
карточки перевозки. Без Docker (`dev.sh`) по умолчанию работает `networkx`; в Docker — Neo4j
(`GRAPH_DB_URL=` пустым отключает его).

Паритет: `tests/test_graphdb.py` сравнивает Neo4j и networkx на всех парах узлов × всех вариантах
блокировок и сквозным прогоном API по всем перевозкам × всем сценариям (результаты должны совпасть
байт в байт). Тесты с Neo4j запускаются при `GRAPH_DB_TEST_URL` (одноразовый экземпляр, данные
`:Hub/:SERVICE` перезаписываются):

```bash
docker run -d --rm --name sct-graph-test -p 127.0.0.1:7687:7687 \
  -e NEO4J_AUTH=neo4j/parity-test-pw neo4j:5.26.10-community
GRAPH_DB_TEST_URL=bolt://127.0.0.1:7687 GRAPH_DB_TEST_PASSWORD=parity-test-pw \
  OMP_NUM_THREADS=1 .venv/bin/python -m pytest -q tests/test_graphdb.py
docker rm -f sct-graph-test
```

## API

Все маршруты, кроме `/api/health`, требуют bearer-токен.

| Метод и путь | Назначение |
|---|---|
| `GET /api/health` | Проверка (публичный); `graph_backend`: `neo4j` или `networkx` |
| `GET /api/catalog` | Узлы и сервисы каталога |
| `GET /api/dashboard` | Перевозки, риски, сводка для «Обзора» |
| `GET /api/shipments/{id}` | Двойник перевозки: погода, сценарий, прогноз, маршрут, альтернативы, декларация |
| `POST /api/shipments/{id}/scenario`, `/scenario/reset` | Сценарий `storm` / `congestion` / `closure`; сброс |
| `POST /api/shipments/{id}/route` | Выбор маршрута (симуляция, не бронирование) |
| `GET /api/hubs/forecast?shipment_id=…` | Загрузка узлов и узкие места на 72 ч |
| `GET /api/summary?weeks=4\|13` | Сводка по коридору для страницы «Сводка» |
| `GET /api/model/metrics` | Метрики модели на отложенной выборке |
| `GET /api/preclearance/ruleset` | Набор правил `rules-v1`: правила R1–R5, параметры, `ruleset_hash` |
| `GET`/`PUT /api/shipments/{id}/preclearance` | Чтение / сохранение версии декларации |
| `POST …/preclearance/validate`, `…/submit`, `…/review` | Проверка; отправка (`Idempotency-Key`, логист; результат правил в поле `clearance`, статус `auto_accepted` или `submitted`); решение (проверяющий, только из `submitted`) |
| `GET /api/shipments/{id}/audit`, `/audit/verify` | Журнал; проверка хеш-цепочки и сверка с реестром (блок `ledger`) |
| `GET /api/shipments/{id}/ledger` | Состояние узлов-свидетелей: кворум, закреплённая длина, статус каждого узла |

Контракты полей — `docs/CONTRACTS.md`.

## Ограничения

История, расписания и грузы синтетические; часы симуляции зафиксированы на 12 ноября 2026,
08:00 UTC, seed=42. Текущая погода по умолчанию живая: `backend/app/weather.py` одним пакетным
запросом берёт ветер на 10 м (м/с) и осадки из Open-Meteo Forecast и высоту волны из Open-Meteo
Marine для всех узлов каталога (ключ не нужен, таймаут 3 с, кэш в памяти 30 мин). Она применяется
как текущие условия к фиксированному расписанию; сценарий «Шторм» по-прежнему переопределяет ветер
и волну. При любой ошибке (таймаут, не-200, редирект с Open-Meteo, битый или слишком большой ответ)
используется последнее живое наблюдение (`source: cache`), а без него — синтетическая таблица
(`source: synthetic`, `fallback: true`); повтор через 2 мин. Для порта без морских данных (Оля)
волна оценивается по ветру (`wave_estimated: true`). UI подписывает источник: «Open-Meteo, 13.11
09:00 UTC» или «резервные данные». Тесты всегда работают офлайн (`WEATHER_PROVIDER=synthetic`
в `tests/conftest.py`).
Метрики ML оценивают только отложенную синтетическую историю, не реальные перевозки.
CO₂e — оценка оставшихся участков с иллюстративными коэффициентами `v1`; методика в `docs/ESG.md`.

- Расписания, координаты, вместимость и стоимость иллюстративны; AIS не подключён.
- Прогноз загрузки узлов: синтетический фон плюс демо-перевозки; мощности узлов — параметры
  демо-масштаба. Уже в базовом сценарии на Махачкале есть короткое окно ≈ 92 % (синтетический фон).
- Волнение: синтетическое значение по порту или оценка по ветру; сценарий «Шторм» задаёт 4,5 м.
  Это не навигационный прогноз.
- «Сводка»: недельный тоннаж и KPI из синтетической истории; CO₂e истории — масса × средняя
  интенсивность текущих маршрутов, т. е. иллюстрация, не измерение.
- Выбор маршрута не бронирует перевозку; «Одобрена автоматически» и «Принята» не являются
  таможенным выпуском, внешний таможенный шлюз не подключён.
- Правила `rules-v1` иллюстративны (списки доверенных отправителей, кодов, стран выдуманы для демо).
- Хеш-цепочка аудита обнаруживает обычное изменение данных, но не является электронной подписью.
- Реестр — прототип: в Docker три узла — отдельные сервисы, но на одном хосте у одного оператора
  (без Docker — в одном процессе); симметричный HMAC, dev-ключи по умолчанию не секретны; владелец
  хоста может переписать и узлы. В режиме без сети при базе в памяти реестр выключен.

## Доступ и состояние

Демо-токены: `dev-broker-token` (логист), `dev-reviewer-token` (проверяющий).
Переопределение: `BROKER_TOKEN`, `REVIEWER_TOKEN`; значения вводятся в интерфейсе.
Сервисы слушают localhost (в Docker API — только loopback контейнера). Все запросы к `/api`, кроме `/api/health`, включая чтение (GET),
требуют bearer-токен; решение проверяющего — отдельную роль.
Декларации и журнал сохраняются в SQLite (`DATABASE_PATH`, по умолчанию
`./smart_caspian_demo.sqlite3`). Сценарии и выбор маршрута — однопользовательское состояние
процесса, сбрасываются при перезапуске. Выбор маршрута не бронирует перевозку.
Тестовое согласование не является таможенным выпуском. Хеш-цепочка обнаруживает
обычное изменение данных, но не является электронной подписью; узлы-свидетели реестра хранятся
рядом с БД (`<DATABASE_PATH>.witness-*.sqlite3`), а в Docker — в томах `witness-N-data`; всё
сбрасывается вместе (`docker compose down -v`).

Защита: `docs/PITCH.md`, `docs/DEMO.md`.

## Безопасность

Модель угроз: локальное демо на синтетических данных для одного оператора на 127.0.0.1.
Не предназначено для публикации в интернет: нет пользователей, TLS, внешнего хранилища секретов.
Защита рассчитана на случайный доступ из локальной сети/браузера, а не на целевую атаку.

Чтение тоже требует токен (без токена — `401`; публичен только `/api/health`):
`curl -H "Authorization: Bearer dev-broker-token" http://127.0.0.1:8000/api/dashboard`.
Встроенные `demo-*-token` принимаются только от loopback-клиента без заголовков проксирования
(`Forwarded`, `X-Forwarded-For`, `X-Real-IP`). Запросы браузера с чужого сайта
(`Sec-Fetch-Site: cross-site`, Origin не из CORS-списка) отклоняются с `403`; блокировку после
неудачных попыток вызывают только запросы, в которых токен был предъявлен.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BROKER_TOKEN` / `REVIEWER_TOKEN` | `dev-broker-token` / `dev-reviewer-token` | Bearer-токены ролей |
| `DISABLE_DEFAULT_TOKENS` | выкл. | `1` — встроенные токены не принимаются вообще |
| `ENABLE_API_DOCS` | выкл. | `1` — включить `/docs`, `/redoc`, `/openapi.json` |
| `ALLOWED_HOSTS` | — | Доп. имена в заголовке Host (всегда: localhost, 127.0.0.1, [::1]) |
| `MAX_BODY_BYTES` | 65536 | Максимальный размер тела запроса |
| `RATE_LIMIT_PER_MINUTE` | 600 | Лимит запросов на клиента в минуту |
| `AUTH_FAIL_LIMIT` / `AUTH_FAIL_WINDOW_SECONDS` | 20 / 300 | Блокировка после неудачных попыток аутентификации |
| `AUDIT_HMAC_KEY` | — | HMAC-SHA256 для цепочки аудита, не короче 16 символов (иначе сервер не стартует); при включении или смене начните с новой БД |
| `LEDGER_WITNESS_KEYS` | dev-ключи (не секрет) | `witness-1=<key>,witness-2=<key>,witness-3=<key>`, ключи от 16 символов; одно значение для API и узлов (каждый узел берёт свой); при смене начните с новой БД |
| `LEDGER_WITNESS_URLS` | — (узлы в процессе API) | Адреса узлов: три URL по порядку или `witness-1=http://…,…`; в compose — `http://witness-N:8100`. Неверный формат — сервер не стартует |
| `LEDGER_WITNESS_TIMEOUT` | 1.5 | Таймаут запроса к узлу, секунды (запросы к узлам идут параллельно) |
| `DATABASE_PATH` | `./smart_caspian_demo.sqlite3` | Файл SQLite (файлы узлов реестра — рядом, если `LEDGER_WITNESS_URLS` не задан) |
| `WEATHER_PROVIDER` | `open-meteo` | `open-meteo` — живая погода с резервом на синтетику; `synthetic` — полностью офлайн |

Шаблон — `.env.example`; `dev.sh` читает `.env` как строки `KEY=VALUE` (не исполняет его).
Сильный токен/ключ: `python -c "import secrets; print(secrets.token_urlsafe(32))"`.
`dev.sh` запускает uvicorn с `--no-server-header --no-proxy-headers`: поддельный
`X-Forwarded-For` не меняет адрес клиента для rate limit и проверки loopback.

Если открывать доступ за пределы localhost:
- задайте оба токена (разные, сильные) и `DISABLE_DEFAULT_TOKENS=1` — за обратным
  прокси на той же машине все клиенты выглядят как 127.0.0.1;
- публикуйте только через reverse proxy с TLS; uvicorn оставьте на 127.0.0.1;
- добавьте внешнее имя в `ALLOWED_HOSTS`; задайте `AUDIT_HMAC_KEY` (с новой БД);
- rate limiter и счётчик неудачных входов — в памяти одного процесса: не масштабируются
  на несколько воркеров/реплик, сбрасываются при перезапуске, а за прокси все клиенты делят
  один лимит;
- перед передачей проекта удалите локальную `smart_caspian_demo.sqlite3` и `.env`.

Рекомендуется (здесь не выполнялось): зафиксировать зависимости с хешами и проверить их.

```bash
.venv/bin/python -m pip install pip-tools pip-audit
.venv/bin/pip-compile --generate-hashes -o requirements.lock requirements.txt
.venv/bin/pip-compile --generate-hashes -o requirements-dev.lock requirements-dev.txt
.venv/bin/pip-audit -r requirements.lock --require-hashes
.venv/bin/python -m pip install --require-hashes -r requirements.lock
npm --prefix frontend audit
```
