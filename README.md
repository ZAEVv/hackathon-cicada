# Smart Caspian Transit

Рабочий прототип кейса 2 «Предиктивный цифровой двойник мультимодального хаба» (трек «Цифровая
экосистема МТК Север–Юг»): прогноз стыковок и загрузки узлов, цифровой коридор pre-clearance и
единое окно логиста. Все данные синтетические.

Полный разбор устройства проекта и ответы на вопросы жюри: [docs/PROJECT_GUIDE_RU.md](docs/PROJECT_GUIDE_RU.md).

## Запуск

### Docker (рекомендуется для показа)

```bash
docker compose up -d --build
```

Интерфейс: http://127.0.0.1:5173. Один контейнер, два процесса: API слушает только loopback
контейнера (`127.0.0.1:8000`), наружу опубликован только UI (`vite preview`), который проксирует
`/api`. Порт публикуется на `127.0.0.1` хоста. Проверка: `curl http://127.0.0.1:5173/api/health`.
Контейнер работает от непривилегированного пользователя, с `read_only`, `cap_drop: ALL`;
SQLite лежит в томе `caspian-data` (сброс чистой БД: `docker compose down -v`).
Опциональные переменные (`DEMO_BROKER_TOKEN`, `DEMO_REVIEWER_TOKEN`, `DEMO_DISABLE_DEFAULT_TOKENS`,
`ENABLE_API_DOCS`, `AUDIT_HMAC_KEY`, `LEDGER_WITNESS_KEYS`) передаются из окружения или `.env` рядом с `docker-compose.yml`.

### Без Docker

Нужны Python 3.11+ и Node.js 20+ с npm.

```bash
./scripts/dev.sh
```

Интерфейс: http://127.0.0.1:5173 · API: http://127.0.0.1:8000/api/health
(OpenAPI `/docs` выключен по умолчанию, включается `ENABLE_API_DOCS=1`).

Зависимости: `requirements.txt` — только runtime, `requirements-dev.txt` — плюс pytest/httpx
для тестов (`dev.sh` ставит его). Локальные настройки: `cp .env.example .env`, см. «Безопасность».
Автоматический сквозной сценарий при запущенном API: `.venv/bin/python scripts/demo.py`
(по умолчанию `http://127.0.0.1:8000`; для Docker — `--base-url http://127.0.0.1:5173` или
`SCT_BASE_URL=...`). Печатает PASS/FAIL по каждой проверке, при ошибке код выхода ≠ 0.
Пошаговый сценарий показа на 5–7 минут — `docs/DEMO.md`.

## Что делает прототип

Каталог (синтетический): западная линия Астрахань (ж/д терминал) → Махачкала / Оля → Энзели →
Тегеран и восточная ветка Актау, Туркменбаши, Амирабад (сервисы `rail-east`, `sea-aktau`,
`rail-kz-tm`, `sea-tkm`, `sea-mak-amirabad`, `rail-amirabad`). Шесть перевозок SCT-001…SCT-006;
SCT-004…006 идут по восточной ветке.

Сквозной сценарий: событие («Шторм» / «Очередь» / «Закрытие») → прогноз готовности и риск
пропуска стыковки → прогноз загрузки узлов на 72 ч и узкие места → допустимые альтернативы с ETA,
стоимостью и CO₂e → выбор маршрута → предварительная декларация → тестовое решение → аудит.

| Требование кейса | Где реализовано | Что показать |
|---|---|---|
| **1. Предиктивная модель** (задержка, готовность, риск пропуска, узкие места хаба, волнение моря) | `backend/app/predictive.py` (монотонный Gradient Boosting `gbm-demo-v3` + baseline, временное разделение; признаки: очередь, ветер, осадки, известная задержка, масса, `wave_height_m`); `backend/app/hubs.py` (почасовая загрузка узлов на 72 ч); `GET /api/shipments/{id}`, `GET /api/hubs/forecast`, `GET /api/model/metrics` | `#/overview/SCT-001` → «Шторм»: риск «Высокий», фактор «Сильное волнение» (4,5 м), готовность после дедлайна приёма; слой «Загрузка узлов», ползунок «Горизонт прогноза», карточка «Узкие места · 72 ч» (Махачкала, пик ≈ 161 %); `#/model` (MAE, baseline, ROC AUC) |

уведомления (toast) о действиях, светлая и тёмная темы.

### Цифровой коридор: правила, аудит, реестр

- **Предзаполненная декларация.** Новая декларация открывается с демо-значениями (отправитель
  «Demo Russian Exporter», HS 847990, страна RU, документы `INV-/PL-/CMR-<id>`, масса и контейнер
  перевозки), поэтому основной путь — три действия: «Сохранить черновик» → «Проверить» → «Отправить».
- **Набор правил `demo-rules-v1`** (`preclearance.py`) — детерминированная проверка при отправке:
  R1 документы согласованы с декларацией (контейнер, массы ±1 кг); R2 код ТН ВЭД не из списка
  ручного контроля (префиксы 93, 2844, 3601–3604); R3 стоимость за кг в диапазоне 0,05–500 $;
  R4 отправитель в списке доверенных (Demo Russian / Kazakh / Iranian Exporter); R5 страна
  происхождения из списка (RU, KZ, IR, AZ, TM, UZ). Все пять пройдены → статус `auto_accepted`
  («Одобрена автоматически»); иначе `submitted` («На рассмотрении») и решение отдельной роли
  проверяющего. Решение, id и SHA-256 хеш набора правил (`ruleset_hash`) записываются в запись
  аудита `submit`; определение правил — `GET /api/preclearance/ruleset`. Списки и пороги
  иллюстративны, это не таможенные правила.
- **Хеш-цепочка аудита**: каждая операция — запись с `previous_hash` и SHA-256 (или HMAC при
  `AUDIT_HMAC_KEY`); `GET …/audit/verify` проверяет порядок, связи и соответствие текущей декларации.
- **Прототип распределённого реестра** (`ledger.py`): три узла-свидетеля `customs-ru`,
  `customs-ir`, `port-operator` (в UI — «Таможня РФ», «Таможня Ирана», «Оператор порта»), у каждого
  свой файл SQLite (`<db>.witness-<id>.sqlite3`) и свой HMAC-ключ. После каждой записи аудита
  узлы принимают только продолжение своей цепочки (следующий номер и верный `previous_hash`) и
  подписывают `(shipment_id, sequence, hash, previous_hash, at)`; запись «закреплена» при 2 из 3.
  Сверка (`GET …/ledger` и блок `ledger` в `…/audit/verify`) обнаруживает переписывание или
  удаление локальной истории после закрепления — даже если цепочка внутри основной БД
  пересчитана целиком. Честно: узлы работают **в одном процессе на одном диске**, ключи
  симметричные и по умолчанию детерминированные демо-ключи (`LEDGER_WITNESS_KEYS` для замены),
  проверяющий знает все ключи; узлы видят только хеши, а не содержание документов; консенсуса,
  сети и защиты от владельца хоста нет. Это модель того, как работал бы permissioned-реестр
  с независимыми операторами и асимметричными подписями, а не сам такой реестр.

### Метрики модели

Прогон на отложенной синтетической выборке (`gbm-demo-v3`, seed 42; 576 строк обучения,
144 теста, граница разделения 2026-10-25T09:07:15Z): MAE модели 0,44 ч против 2,86 ч у baseline
(медиана train); ROC AUC 1,0. Значение 1,0 — артефакт генератора: в синтетической истории метка «пропуск» почти детерминированно задаётся запасом времени до дедлайна, а он известен на входе (ранжирование только по запасу тоже даёт 1,0, по одному прогнозу задержки — 0,976). Это не точность на реальных рейсах; содержательная метрика — MAE. Подробно: `docs/PROJECT_GUIDE_RU.md`.

### Демо-баланс (базовый сценарий, чистый запуск)

- «Перевозки под риском»: 3 из 6 (счётчик: высокий риск модели или пропущенная стыковка; SCT-002 и
  SCT-003 на западной линии через Олю — риск «Средний», SCT-006 на восточной ветке — «Высокий»).
- SCT-001: риск «Низкий», готовность 12 ноября ≈ 11:35Z при дедлайне приёма 14:00Z, ETA 14 ноября 06:00Z.
- Прогноз узлов: одно короткое окно в Махачкале 12 ноября 16:00–18:00Z, пик ≈ 92 % (синтетический фон).
- «Шторм» на SCT-001: ветер 22 м/с, волна 4,5 м, прибытие +3 ч, очередь +2 ч → готовность 13 ноября

## API

Все маршруты, кроме `/api/health`, требуют bearer-токен.

| Метод и путь | Назначение |
|---|---|
| `GET /api/health` | Проверка (публичный) |
| `GET /api/catalog` | Узлы и сервисы каталога |
| `GET /api/dashboard` | Перевозки, риски, сводка для «Обзора» |
| `GET /api/shipments/{id}` | Двойник перевозки: погода, сценарий, прогноз, маршрут, альтернативы, декларация |
| `POST /api/shipments/{id}/scenario`, `/scenario/reset` | Сценарий `storm` / `congestion` / `closure`; сброс |
| `POST /api/shipments/{id}/route` | Выбор маршрута (симуляция, не бронирование) |
| `GET /api/hubs/forecast?shipment_id=…` | Загрузка узлов и узкие места на 72 ч |
| `GET /api/summary?weeks=4\|13` | Сводка по коридору для страницы «Сводка» |
| `GET /api/model/metrics` | Метрики модели на отложенной выборке |
| `GET /api/preclearance/ruleset` | Набор правил `demo-rules-v1`: правила R1–R5, параметры, `ruleset_hash` |
| `GET`/`PUT /api/shipments/{id}/preclearance` | Чтение / сохранение версии декларации |
| `POST …/preclearance/validate`, `…/submit`, `…/review` | Проверка; отправка (`Idempotency-Key`, логист; результат правил в поле `clearance`, статус `auto_accepted` или `submitted`); решение (проверяющий, только из `submitted`) |
| `GET /api/shipments/{id}/audit`, `/audit/verify` | Журнал; проверка хеш-цепочки и сверка с реестром (блок `ledger`) |
| `GET /api/shipments/{id}/ledger` | Состояние узлов-свидетелей: кворум, закреплённая длина, статус каждого узла |

Контракты полей — `docs/CONTRACTS.md`.

## Ограничения

По умолчанию всё демо автономно: история, расписания, грузы и погода синтетические.
Часы симуляции зафиксированы на 12 ноября 2026, 08:00 UTC, seed=42.
Опциональный адаптер Open-Meteo доступен в модуле данных; основной сценарий не смешивает
реальную текущую погоду с фиксированным демонстрационным временем.
Метрики ML оценивают только отложенную синтетическую историю, не реальные перевозки.
CO₂e — оценка оставшихся участков с иллюстративными коэффициентами `demo-v1`; методика в `docs/ESG.md`.

- Расписания, координаты, вместимость и стоимость иллюстративны; AIS не подключён.
- Прогноз загрузки узлов: синтетический фон плюс демо-перевозки; мощности узлов — параметры
  демо-масштаба. Уже в базовом сценарии на Махачкале есть короткое окно ≈ 92 % (синтетический фон).
- Волнение: синтетическое значение по порту или оценка по ветру; сценарий «Шторм» задаёт 4,5 м.
  Это не навигационный прогноз.
- «Сводка»: недельный тоннаж и KPI из синтетической истории; CO₂e истории — масса × средняя
  интенсивность текущих маршрутов, т. е. иллюстрация, не измерение.
- Выбор маршрута не бронирует перевозку; «Одобрена автоматически» и «Принята в демо» не являются
  таможенным выпуском, внешний таможенный шлюз не подключён.
- Правила `demo-rules-v1` иллюстративны (списки доверенных отправителей, кодов, стран выдуманы для демо).
- Хеш-цепочка аудита обнаруживает обычное изменение данных, но не является электронной подписью.
- Реестр — прототип: три узла в одном процессе и на одном диске, симметричный HMAC, демо-ключи
  по умолчанию не секретны; владелец хоста может переписать и узлы. При базе в памяти реестр выключен.

## Доступ и состояние

Демо-токены: `demo-broker-token` (логист), `demo-reviewer-token` (проверяющий).
Переопределение: `DEMO_BROKER_TOKEN`, `DEMO_REVIEWER_TOKEN`; значения вводятся в интерфейсе.
Сервисы слушают localhost (в Docker API — только loopback контейнера). Все запросы к `/api`, кроме `/api/health`, включая чтение (GET),
требуют bearer-токен; решение проверяющего — отдельную роль.
Декларации и журнал сохраняются в SQLite (`DATABASE_PATH`, по умолчанию
`./smart_caspian_demo.sqlite3`). Сценарии и выбор маршрута — однопользовательское состояние
процесса, сбрасываются при перезапуске. Выбор маршрута не бронирует перевозку.
Тестовое согласование не является таможенным выпуском. Хеш-цепочка обнаруживает
обычное изменение данных, но не является электронной подписью; узлы-свидетели реестра хранятся
рядом с БД (`<DATABASE_PATH>.witness-*.sqlite3`, в Docker — в том же томе) и сбрасываются
вместе с ней (`docker compose down -v`).

Защита: `docs/PITCH.md`, `docs/DEMO.md`.

## Безопасность

Модель угроз: локальное демо на синтетических данных для одного оператора на 127.0.0.1.
Не предназначено для публикации в интернет: нет пользователей, TLS, внешнего хранилища секретов.
Защита рассчитана на случайный доступ из локальной сети/браузера, а не на целевую атаку.

Чтение тоже требует токен (без токена — `401`; публичен только `/api/health`):
`curl -H "Authorization: Bearer demo-broker-token" http://127.0.0.1:8000/api/dashboard`.
Встроенные `demo-*-token` принимаются только от loopback-клиента без заголовков проксирования
(`Forwarded`, `X-Forwarded-For`, `X-Real-IP`). Запросы браузера с чужого сайта
(`Sec-Fetch-Site: cross-site`, Origin не из CORS-списка) отклоняются с `403`; блокировку после
неудачных попыток вызывают только запросы, в которых токен был предъявлен.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DEMO_BROKER_TOKEN` / `DEMO_REVIEWER_TOKEN` | `demo-broker-token` / `demo-reviewer-token` | Bearer-токены ролей |
| `DEMO_DISABLE_DEFAULT_TOKENS` | выкл. | `1` — встроенные токены не принимаются вообще |
| `ENABLE_API_DOCS` | выкл. | `1` — включить `/docs`, `/redoc`, `/openapi.json` |
| `ALLOWED_HOSTS` | — | Доп. имена в заголовке Host (всегда: localhost, 127.0.0.1, [::1]) |
| `MAX_BODY_BYTES` | 65536 | Максимальный размер тела запроса |
| `RATE_LIMIT_PER_MINUTE` | 600 | Лимит запросов на клиента в минуту |
| `AUTH_FAIL_LIMIT` / `AUTH_FAIL_WINDOW_SECONDS` | 20 / 300 | Блокировка после неудачных попыток аутентификации |
| `AUDIT_HMAC_KEY` | — | HMAC-SHA256 для цепочки аудита, не короче 16 символов (иначе сервер не стартует); при включении или смене начните с новой БД |
| `LEDGER_WITNESS_KEYS` | демо-ключи (не секрет) | `customs-ru=<key>,customs-ir=<key>,port-operator=<key>`, ключи от 16 символов; при смене начните с новой БД |
| `DATABASE_PATH` | `./smart_caspian_demo.sqlite3` | Файл SQLite (файлы узлов реестра — рядом) |

Шаблон — `.env.example`; `dev.sh` читает `.env` как строки `KEY=VALUE` (не исполняет его).
Сильный токен/ключ: `python -c "import secrets; print(secrets.token_urlsafe(32))"`.
`dev.sh` запускает uvicorn с `--no-server-header --no-proxy-headers`: поддельный
`X-Forwarded-For` не меняет адрес клиента для rate limit и проверки loopback.

Если открывать доступ за пределы localhost:
- задайте оба токена (разные, сильные) и `DEMO_DISABLE_DEFAULT_TOKENS=1` — за обратным
  прокси на той же машине все клиенты выглядят как 127.0.0.1;
- публикуйте только через reverse proxy с TLS; uvicorn оставьте на 127.0.0.1;
- добавьте внешнее имя в `ALLOWED_HOSTS`; задайте `AUDIT_HMAC_KEY` (с новой БД);
- rate limiter и счётчик неудачных входов — в памяти одного процесса: не масштабируются
  на несколько воркеров/реплик, сбрасываются при перезапуске, а за прокси все клиенты делят
